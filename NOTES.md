## 1. What I built and why

**Newsletter signup.** I added a `subscriber` document type and `POST /api/newsletter`. The route checks the rate limit first, then body size, then a honeypot field, then the email, and writes with the write token on the server. The document ID is a hash of the email, so the same address twice finds the same document instead of making a second one. New and existing emails get the exact same reply, so the form can't be used to check who is on the list. The page builder never passed an `action` to the newsletter block, so I wrapped it in a small client component. The form has a real `action`, so it still works without JavaScript (a 303 redirect back to the page), and with JavaScript it shows the message inline. The page the signup came from is saved as the source, and I only accept a path on our own site so the redirect can't point anywhere else. **The rate limit is 5 tries per 10 minutes per IP.** It lives in `apps/web/src/lib/rate-limit.ts`, a sliding window log on Upstash Redis, and the IP is hashed before it is stored. If Upstash is not set or is down, it falls back to an in-memory limit per instance instead of letting everything through. A call that could have gone the other way: I wrote the limiter myself instead of adding `@upstash/ratelimit`, because it is only a few Redis commands and I didn't want a new dependency. I also chose a honeypot over a captcha, because a captcha makes the form worse for real people.

**Sync to Algolia.** A Sanity webhook (filter: published blog posts only) calls `/api/webhooks/algolia`. I check the signature myself, an HMAC of the timestamp and the raw body, compared in constant time, and anything missing or wrong is a 401. I didn't use `next-sanity`'s `parseBody` because the library under it compares with `!==` and returns null instead of false when the secret is missing. The webhook only sends the ID. The route then reads the current published post from Sanity and decides from that: if it should be in search it gets saved, otherwise (unpublished, deleted, Do Not Index, hidden from lists) it gets removed. I did it this way so the order or number of deliveries doesn't matter, the latest state always wins. The `objectID` is the Sanity `_id`, so a repeated delivery overwrites the same record. Any `_id` with a dot (`drafts.` or `versions.`) is skipped as a second check after the webhook filter, and other document types get a 200 with "skipped" so Sanity doesn't keep retrying them. Sanity's read can be a moment behind the publish that fired the webhook, so if the post looks older than the event it waits 1 second and reads again, and if it is still behind it returns 503 so Sanity retries. I left out a timestamp age check for replays on purpose: replaying an old delivery only makes the route sync the current state again, which is harmless. That one could have gone the other way.

**Backfill.** `apps/web/scripts/backfill-algolia.ts`, run from `apps/studio` with `pnpm backfill:algolia`. It uses the same query, the same "should this be in search" rule and the same record shape as the webhook, so both always write the same thing. It also removes records that shouldn't be in the index anymore, and `--dry-run` shows what it would do without writing. Running it twice is safe because the IDs are the same. The index settings (`searchableAttributes`: title, description, author name, `attributesForFaceting`: category, ranking: newest first) are set by the script so they live in code. I run it with `sanity exec` because `node --experimental-strip-types` failed on the repo's imports without file extensions, and `tsx` would be a new dependency.

**Search.** `/api/blog/search` stays on the server and queries Algolia with the search-only key, so the route never holds a key that can write. The response is `{ hits, page, totalPages, total, source }` with 9 results per page, the same as the blog list grid, and I updated the hook and the results UI with paging and a category filter. **The rate limit is 30 requests per minute per IP**, in the same `rate-limit.ts`, checked before anything else. Search runs as you type, so I wanted room for a real person but not for a script running up the Algolia bill. `q` is required and at most 100 characters, `page` is a whole number from 1 to 50, and `category` has to be one of the known values, because it goes inside an Algolia filter string and a free text value could change the filter. **When Algolia is down** (an error, or no answer within 2.5 seconds), the route falls back to the old Sanity search (GROQ plus Fuse) with the same response shape and `"source":"fallback"`, and if that fails too it returns 503. I chose a fallback over an error because search is a normal part of the blog page and the posts are already in Sanity. The fallback is slower and less accurate, but for a few dozen posts I think it is better than a broken search box. The fallback only reads published posts, so it can't show drafts either. A call that could have gone the other way: searching from the browser straight to Algolia would be faster, but then I couldn't rate limit it or fall back.

**Studio "SEO & Index" tab.** A second view next to the form, only for blog posts. It reads the live draft that Studio hands the component, so the preview and checks update while typing, before saving. The preview uses the SEO fields with the fallbacks from `seo-fields.ts`, and truncates the way a search result does. There are four checks, always shown with pass or fail and live character counts: meta title, description length, image, and Do Not Index. The description uses 140 to 160, the same as the `blog` schema. **There is no title limit in the schema, so I used 60 characters.** From what I read, Google usually cuts titles at around 60 characters (it really cuts by pixel width, so it's not exact), and it's a common limit in SEO tools. The index status looks up the post in Algolia by `objectID` with the search-only key, because this runs in the browser, and compares it with the published version. That way it can say "published but missing from the index" or "Do Not Index is on but it's in the index". Right after a publish it says "Search index is updating" and checks once more after 5 seconds, so the editor doesn't see a false red while the webhook is still running.

**Bonus, PageSpeed.** The LCP element was the hero text and most of its time was render delay. The hero animation started at `opacity: 0`, and from what I understand Chrome doesn't count invisible text as painted. I removed only the opacity. The slide and blur are still there, so nothing was traded for score. Render delay went down, but mobile LCP stayed at 2.7 s. The full before and after is in VERIFY.md.

## 2. What I noticed

- **SETUP.md and `package.json` disagree on versions.** SETUP says Node `>=22.12` and `pnpm@10.32.1`, but `package.json` says Node `>=24` and `pnpm@11.24.0`. I think SETUP just wasn't updated when the template moved on, so probably wrong, not deliberate.
- **The default Sanity API version is today's date** (`new Date()` in `@workspace/env/constants`). So the API version changes every day and the app can pick up API changes without anyone deciding to. I think it's deliberate, to always be on the latest, but I would pin a fixed date so the behaviour only changes when someone bumps it.
- **The old search query didn't skip `seoNoIndex` posts.** `queryAllBlogDataForSearch` filters out `seoHideFromLists` but not `seoNoIndex`, so a post marked Do Not Index still showed up in site search. This might be deliberate (Do Not Index is about Google, not your own site search), but the README treats a Do Not Index post sitting in the index as a problem, so I left them out of Algolia.
- **The old search used the page's perspective.** In local dev (`DRAFTS_WITHOUT_SESSION`) or in a Presentation session, it searched drafts. Only people with a draft session could see that, so it's not a leak to the public, but Algolia never has drafts, so I made both new search paths published only.
- **`queryAllBlogDataForSearch` is also used by the markdown route and llms.txt.** The name says search, but other things depend on it. I think the reuse is deliberate, but the name makes it easy to change the query for search and break those. I added a new query instead of changing that one.
- **The revalidate route's secret compare returns early when the lengths differ** (`a.length === b.length && timingSafeEqual(a, b)`). That tells an attacker the secret's length through timing. I think it's very low risk in practice, but hashing both sides to the same length first avoids it, so that's what I did in the webhook check.
- **`SANITY_API_WRITE_TOKEN` was required even though nothing read it** (CLAUDE.md says this too). I think it's deliberate, so features like this one have a token ready, and the newsletter route now uses it.
- **`getPresentationUrl()` in Studio throws when `NODE_ENV` is not `development`** and the URL is unset. That's good for the Presentation tool, but it meant I couldn't reuse it in the SEO tab, because a missing env var would crash the whole tab. I read the env var directly there, like `slug-field-component.tsx` already does.
- **zod ends up in the client bundle** through `@workspace/env/client`. I think it's deliberate, so env vars are checked in the browser too, but it's part of the unused JavaScript PageSpeed complains about on mobile.
- **The footer text has low contrast.** Probably a design choice, but it's an accessibility issue that I'd raise.
- **The newsletter block posted nowhere.** I think this one is deliberate for the test.
- Two about my own setup: `apps/studio/.env.example` has my Algolia app ID and search-only key filled in on purpose, so the SEO tab works right after cloning (the search-only key is safe to share). Vercel Analytics requests return 404 on my deployment, I think because Analytics isn't enabled on my Vercel project.

## 3. What I'd do with more time

- **Newsletter:** a captcha if bots still got past the honeypot and rate limit. A global cap across all IPs, since right now many different IPs could still send a lot together. A secret salt for the IP hash, because without one someone with the Redis data could in theory hash IPs and match them. Double opt-in with a confirmation email.
- **Sync:** a queue if content teams start publishing in big batches. Right now Sanity's retries do that job, and one post per event is small work.
- **Studio:** an Algolia key restricted to only the `blog` index. The search-only key can read every index in the app. There's only one today, but a restricted key would be safer. I'd also share the "should this be in search" rule as one package instead of having it in Studio and web with a comment to keep them in step, and add more checks like image alt text.
- **Search:** highlight the matched words in the results.
- **PageSpeed:** look at the roughly 200 KiB of unused JavaScript, including zod from the env check in the browser. I think that's what still keeps mobile LCP at 2.7 s, but fixing it means changing how env vars reach the client, and I didn't want to risk that for a bonus task.
- **Tests:** a test for the Studio tab. Right now it's only checked by hand and in the recording.
